# Member 2 — Collaboration, review and publication handover

This guide is the consolidated handover for the Member 2 collaboration implementation in the AlphaLab Quant Framework. It replaces the earlier stage-by-stage notes with one maintained reference.

## 1. Scope and current status

The implementation provides a controlled researcher–reviewer workflow for archived AlphaLab backtests:

1. Prepare a candidate from an already persisted backtest.
2. Freeze the report, outputs and supporting evidence in the immutable EvidenceStore.
3. Delegate an independent reviewer through the Conexus collaboration Host.
4. Validate structured review results against the exact candidate and manifest.
5. Support correction, candidate revision, re-review, escalation and shared budget controls.
6. Preflight and publish only the approved report and its three Harness outputs.
7. Preserve prior report revisions and recover publication receipts after interrupted delivery.

**Production integration boundary:** A trusted FastAPI finalization route is now implemented at `POST /api/conexus/collaboration/tasks/{task_id}/finalize`. It accepts only an idempotency key; approvals, evidence, destination revisions and filesystem paths are loaded from trusted task stores. Task stores use deterministic per-task directories under `ALPHALAB_RUNTIME_DIR/collaboration/tasks/`. The route and new storage resolver still require execution of their focused API tests and a full regression run in the recipient's configured Python environment before production use.

The ordinary single-agent workflow remains available and is not replaced by the collaboration utilities.

## 3. Repository layout

Production candidate preparation can create its EvidenceStore with `create_task_evidence_store(task_id)`. The collaboration Host uses the same deterministic roots when `storeRoot` and `evidenceRoot` are omitted. Explicit roots remain supported for isolated tests and fixtures; such stores are not discoverable by the production finalization API.

The handover keeps one generated-workspace directory:

```text
build/
└── member-2/
    ├── README.md
    ├── handover-manifest.json
    ├── conexus-source/       # generated by the build script
    ├── conexus-runtime/      # generated by the build script
    └── fixtures/             # disposable test/acceptance runs
```

Only the README and manifest are shipped. Runtime builds, temporary databases and test fixtures are regenerated when needed. The build script keeps all generated Conexus outputs under this one directory.

The vendored Conexus tree is the original checksum-verified upstream source. Member 2's Local Host changes are stored separately as a reviewed patch. Do not edit the vendored upstream files directly or change `vendor/conexus/EXPORT.json` to conceal a mismatch.


Use the Python executable from the project virtual environment for all tests.

### Environment and credentials

Start from `.env.example`; create an untracked `.env.local` for local values. Never include real provider credentials, workspace tokens or publication secrets in a handover archive.

`ALPHALAB_PUBLICATION_HMAC_SECRET` must be a separately generated secret shared by the trusted Python coordinator and the Local Host. It must not reuse `CONEXUS_LOCAL_TOKEN`. The Local Host connection file is created by the local launcher and is referenced through `ALPHALAB_AGENT_CONNECTION_FILE`.

A model provider is only needed for an explicitly enabled live reviewer run. Scripted acceptance and Local Host publication tests do not make model-provider calls.

## 5. Build the patched Conexus runtime

Run from the project root:

```powershell
& .\.venv\Scripts\python.exe scripts/build_conexus_runtime.py
```

The build performs these checks and operations:

1. Verify every file in `vendor/conexus` against the original `EXPORT.json` hashes.
2. Verify the local patch-set manifest and the patch SHA-256.
3. Copy the clean upstream source to `build/member-2/conexus-source`.
4. Apply the Member 2 publication patch to that disposable copy.
5. Run the open-core boundary check and the upstream TypeScript build.
6. Assemble the runnable runtime at `build/member-2/conexus-runtime` and install its production dependencies.

The upstream export and its hashes remain unchanged. The patch is applied with Git's three-component path stripping because its recorded diff paths include `vendor/conexus/`.

To run the patched Local Host tests, use the patched source workspace, not the untouched vendor tree:

```powershell
Push-Location build/member-2/conexus-source
npm test --workspace @conexus/local-host
Pop-Location
```

The real-process publication acceptance test imports the generated runtime from `build/member-2/conexus-runtime`.

## 6. Candidate preparation and review

Candidate preparation uses an existing backtest. It does not execute a new backtest or publish a report.

The trusted preparation service is:

```text
apps/api/services/agent_collaboration_service.py
```

The production preparation helper is:

```text
scripts/prepare_member2_production_review.py
```

It requires an authorised backtest ID, a draft Markdown report, proposed schema-valid workspace outputs, a request ID, a review question and a genuine claim to be checked. Choose a fresh output directory for each task because task/evidence state is durable.

Example shape:

```powershell
& .\.venv\Scripts\python.exe scripts/prepare_member2_production_review.py `
  --backtest-id YOUR_EXISTING_BACKTEST_ID `
  --output build/member-2/fixtures/production/review-01 `
  --request-id member2-review-01 `
  --question "Review the archived backtest and its supporting evidence." `
  --claim "The archived result reports the performance described in the draft." `
  --report-file build/my-review-draft.md `
  --outputs-file build/my-review-outputs.json
```

Run the scripted Host integration:

```powershell
node scripts/run_member2_production_review.mjs `
  --fixture build/member-2/fixtures/production/review-01/fixture.json `
  --python .venv/Scripts/python.exe
```

Scripted mode is an integration probe, not proof of independent financial reasoning. It intentionally returns an incomplete review. Live reviewer execution requires explicit `--live --confirm-paid` flags and a separately configured provider.

For synthetic acceptance fixtures, use `scripts/prepare_collaboration_acceptance.py` and `scripts/run_member2_review.mjs`. The correction fixture is prepared with `scripts/prepare_member2_correction_fixture.py` and exercised with `scripts/check_member2_correction_loop.mjs`. Store all disposable outputs under `build/member-2/fixtures/`.

## 7. Publication, durability and recovery

The publication path has two independent durable stores. It is not one distributed ACID transaction.

1. **ControlStore:** `prepare_publication()` validates the current approved candidate and records an immutable pending intent, request digest and idempotency key.
2. **Conexus Local Host:** validates the HMAC and expected workspace/report revisions, then stages the report, the three output nodes, report history, workspace revision and receipt in one state-file replacement.
3. **ControlStore:** validates and records the Host receipt.

The Local Host state-file replacement is the publication commit point. A lost HTTP response after that point is an unknown outcome, not proof of failure. Recovery must query the receipt using the same idempotency key and reconcile it into ControlStore. Never create a new idempotency key simply because a request timed out.

The Local Host routes are:

| Method and path | Authentication | Purpose |
|---|---|---|
| `POST /api/alphalab/publications` | Publication HMAC | Validate and atomically commit a reviewed report and workspace outputs. |
| `GET /api/alphalab/publications/:idempotencyKey` | Publication HMAC | Retrieve the durable receipt for retry and recovery. |

The AlphaLab workstation exposes the trusted finalization operation separately:

| Method and path | Authentication | Purpose |
|---|---|---|
| `POST /api/conexus/collaboration/tasks/{task_id}/finalize` | Existing workstation Basic authentication when enabled | Publish the latest passing review or reconcile an existing pending intent. The body contains only `idempotency_key`. |

The route opens existing task databases only. It never creates empty stores for an unknown task and never accepts caller-provided paths, approvals, report content, output payloads or destination revisions. The same endpoint is safe to retry with the same idempotency key; a pending Host receipt returns HTTP 202, while a committed receipt returns HTTP 200.
Previous report content and its candidate/manifest references are retained as report history when a report is updated. The publication path does not modify strategy source files or source-control revisions.

`finalize_collaboration_task()` is intended for trusted application code. It must obtain task approval and frozen evidence from ControlStore/EvidenceStore; it must never accept caller-supplied review approvals or arbitrary filesystem paths.

## 9. Known limitations and handover notes

- The FastAPI finalization route and deterministic task-store resolver have been added. The new API and updated finalization tests are included, but they have not been executed in the assembly environment because its Python interpreter lacks the project's `pyarrow` dependency. Run them in the project's fully installed `.venv` before treating this integration as accepted.
- Production task preparation must use `create_task_evidence_store(task_id)` (or the canonical `data/runtime/collaboration/tasks/{task_id}/evidence` directory), and the collaboration Host must omit explicit store roots so it selects the matching canonical control/evidence directories.
- The API route inherits the existing optional workstation Basic authentication middleware. For any non-loopback deployment, enable and configure `ALPHALAB_WEB_AUTH_ENABLED`, `ALPHALAB_WEB_USERNAME` and `ALPHALAB_WEB_PASSWORD`.
- The local publication HMAC authenticates the trusted coordinator. Review authority is established by Python ControlStore/EvidenceStore preflight, not by the HMAC itself.
- The Host and ControlStore are separate durable stores; recovery is idempotent reconciliation, not a distributed transaction.
- Live model review is optional and has not been established by scripted fixture tests. Scripted reviews must not be represented as model-quality evidence.
- The Conexus source export states `licenseStatus: pending-owner-selection`. Do not describe it as a published open-source release or change its license metadata without owner approval.
- This handover archive intentionally excludes `.git`, `.venv`, `node_modules`, generated build outputs, local runtime databases, provider credentials and temporary review databases. The third member should integrate these source changes into the team's shared Git branch, create their own environment, and rebuild the runtime.
